# Flight Analyzer 同步正确性与性能改造方案

## 1. 背景

当前项目同步少量架次时等待时间较长。一次实际操作中，同步 3 个架次的用户可见等待时间约为 2 分 40 秒。后续项目预计需要处理 10GB 以上的数据，因此既要优化传输和导入性能，也要先保证多个客户端之间的实体身份不会因为本地 ID、名称不同而发生错误拆分或重复导入。

本文记录当前实现、实测结果、已经确认的业务规则、正确性问题以及分阶段改造方案。

## 2. 已确认的数据与业务规则

### 2.1 不可变数据

当前阶段不考虑客户端软件版本不同的问题，并确认：

- 原始飞行文件导入后不会被修改；
- 同一批原始文件产生的解析结果不会被修改；
- 原始文件和解析结果都可以视为不可变数据；
- 同一批原始文件不允许重复导入为两个架次。

因此，原始文件可以按 SHA256 进行内容寻址和去重，架次可以通过其完整原始文件集合进行内容身份判断。

### 2.2 可变元数据

以下信息允许在客户端中修改：

- 机型名称；
- 数据类型别名；
- 数据列别名、单位和展示缩放系数；
- 飞机名称；
- 架次别名；
- 飞行记录单字段。

其中机型的数据类型 key、原始列名、列类型和解析规则属于不可变结构；名称、别名、单位和展示缩放系数不参与机型身份判断。

### 2.3 在线同步的覆盖方向

在线同步由用户选择方向，元数据覆盖规则为：

- 上传：以本地客户端元数据为准，覆盖服务器已有元数据；
- 拉取：以服务器元数据为准，覆盖本地客户端已有元数据；
- 上传架次时，作为依赖携带的飞机元数据也允许覆盖服务器飞机名称；
- 服务器版本号仍可用于预览警告和展示差异，但不应因为服务器版本较新而默认阻止用户明确选择的上传；
- 正式上传前仍必须重新执行服务器预检，避免预览后服务器状态变化导致错误写入。

### 2.4 离线包导入的覆盖方向

外场离线客户端生成同步包后，需要先导入内网客户端。导入预览阶段由用户对整个包选择一种统一策略：

- `package_wins`：包内可变元数据覆盖内网客户端已有元数据；
- `target_wins`：内网客户端已有可变元数据保持不变。

第一版不支持逐实体或逐字段选择不同方向。无论选择哪种策略：

- 新实体都使用包内元数据创建；
- 不可变结构只校验，不按覆盖策略修改；
- 相同原始文件集合的架次不重复导入；
- 如果包内实体在目标客户端创建为一条新记录，则继承包内 `client_uid`；
- 如果包内实体映射到目标客户端已有记录，则保留目标记录原有 `client_uid`，不使用包内 UID 覆盖；
- 如果用户明确把包内实体复制为一个新的独立实体，则生成新的 `client_uid`；
- 客户端之间的离线包导入不写服务器 `sync_entity_mappings`，该映射表只用于客户端上传服务器时缓存客户端身份与服务器实体的对应关系；
- 如果名称覆盖会与另一个不同实体的唯一名称冲突，则停止导入并要求用户先处理，不自动加后缀，也不自动合并。

## 3. 当前同步流程

当前同步以 `.fapkg` ZIP 包为传输单位，完整同步流程如下：

1. 用户打开同步预览。
2. 客户端生成裁剪后的 `parsed.sqlite`。
3. 客户端校验原始文件大小和 SHA256，并将 manifest、解析数据库、模型配置和原始文件压缩为同步包。
4. 客户端将 manifest 发送至服务器进行预检。
5. 用户确认同步。
6. 客户端再次从头生成同一批数据的同步包。
7. 客户端再次预检并上传整个同步包。
8. 服务器保存上传临时文件，解压 `parsed.sqlite` 并校验。
9. 服务器将解析数据批量写入 MySQL，并逐个提取、校验和保存原始文件。
10. 服务器保存一份完整同步包作为归档。
11. `run` 模式继续检查服务器变更；如果存在其他来源的数据，则生成拉取包、下载并导入本地数据库。

正式上传使用约 1MB 分块进行流式网络发送，没有把整个同步包一次性加载到客户端内存中。当前主要瓶颈位于传输前后的数据加工、临时文件读写和数据库导入阶段。

## 4. 实测结果

### 4.1 一次完整同步耗时

根据本地 `sync_runs` 记录和同步包生成时间还原，一次 3 架次同步的耗时如下：

| 阶段 | 耗时 |
| --- | ---: |
| 同步预览打包 | 12 秒 |
| 用户确认后的正式打包 | 12 秒 |
| 上传及服务器导入 | 54 秒 |
| 拉取及本地导入 | 49 秒 |
| 从预览开始到同步结束 | 160 秒 |

重复预览打包的问题明确存在，但只占本次总耗时约 12 秒。上传及服务器导入、拉取及本地导入合计约 103 秒，才是进一步优化的主要区间。当前缺少服务器内部和本地导入的分阶段指标，因此不能仅凭这一次记录断定数据库 INSERT 是唯一主要瓶颈。

耗时与“架次数”不直接成正比，真正决定耗时的是：

- 原始文件总字节数和文件数量；
- 解析数据总行数、列数和单行宽度；
- 首次全量还是日常增量；
- 服务器需要新增或更新的数据量；
- 同步后是否还需要拉取其他来源的数据；
- 网络带宽、磁盘、CPU 和 MySQL 配置。

### 4.2 当前待上传架次基准

对当前一个待上传架次进行了临时目录打包基准：

| 指标 | 数值 |
| --- | ---: |
| 原始文件数量 | 9 |
| 原始文件大小 | 62,378,202 字节 |
| 解析数据行数 | 378,118 行 |
| 生成的 `parsed.sqlite` | 76,115,968 字节 |
| 最终同步包 | 10,651,083 字节 |
| 单次打包耗时 | 12.8 秒 |

单次打包的主要耗时：

| 操作 | 累计耗时 |
| --- | ---: |
| 生成裁剪后的 `parsed.sqlite` | 约 10.4 秒 |
| ZIP 压缩写入 | 约 2.1 秒 |
| 原始文件 SHA256 校验 | 约 0.3 秒 |

本组数据压缩效果很好：同步包内未压缩数据约 138.6MB，压缩后约 10.6MB。因此在当前样本中，ZIP 压缩和网络字节数不是首要瓶颈；解析数据库生成和两端导入更值得优先测量。

### 4.3 本地同步包积累

当前 `sync_exports` 目录已有 13 个同步包，总大小约 136MB。现有实现没有自动清理同步预览包、成功上传后的临时同步包和拉取缓存。

## 5. 当前实现的主要问题

### 5.1 同一批上传数据被完整打包两次

上传预览会调用 `export_package()` 生成完整同步包：

- `backend/sync/workflow.py:148`

用户确认上传后，正式上传流程再次调用 `export_package()`：

- `backend/sync/workflow.py:381`

前端只会复用拉取预览产生的 `package_path`，上传流程没有复用预览包：

- `frontend/src/pages/SyncPage.tsx:141`

这会导致同一批数据在上传前被查询、复制、哈希和压缩两次。应改为轻量预览，而不是继续依赖完整预览包。

### 5.2 客户端导出和本地拉取导入存在全量加载

客户端生成 `parsed.sqlite` 时，对动态数据表执行 `fetchall()`，随后又构造一份用于 `executemany()` 的 Python 列表：

- `backend/sync/package.py:200`
- `backend/sync/package.py:212`

本地导入服务器拉取包时，同样会全量读取动态表并构造插入列表：

- `backend/sync/local_import.py:1327`
- `backend/sync/local_import.py:1331`

服务端生成拉取包时也存在全量读取：

- `backend/sync/server.py:1732`

这些路径的内存峰值会随单表数据量增长。

### 5.3 服务端动态数据导入已经分批，但吞吐量仍未测清

服务端动态表导入当前已经使用 `fetchmany(DYNAMIC_INSERT_BATCH_SIZE)` 分批读取：

- `backend/sync/server.py:1216`

随后通过 SQLAlchemy/PyMySQL 批量 INSERT：

- `backend/sync/server.py:1229`

因此“服务端导入仍使用 `fetchall()`”不是准确描述。真正需要确认的是：

- 每批行数是否合理；
- Python 行转换耗时；
- MySQL 实际写入吞吐量；
- DELETE 旧架次数据、INSERT 新数据和事务提交分别耗时多少；
- 原始文件解压、校验和归档占多少时间。

在增加分阶段指标前，不应直接决定必须迁移到 Parquet 或 `LOAD DATA`。

### 5.4 大量 ID 和 manifest 仍可能随规模增长

即使把动态数据读取改成 `fetchmany()`，以下对象仍可能随总数据量增长：

- Python 中的架次、飞机和机型 ID 集合；
- manifest 中的全部实体和原始文件条目；
- SQL `IN (...)` 中展开的大量 ID；
- 每批读取后重新构造的 Python 参数列表。

因此“内存固定上限”不能只通过替换 `fetchall()` 实现。大量架次或大量小文件场景还需要 ID 分批、临时选择表或分页 manifest。

### 5.5 文件存在重复读写和重复校验

一次正式上传中包含多次读取、哈希、压缩、解压和复制：

1. 客户端读取解析数据并写入临时 `parsed.sqlite`；
2. 客户端重新读取 `parsed.sqlite` 计算 SHA256；
3. 客户端重新读取原始文件计算 SHA256；
4. 客户端再次读取原始文件和 `parsed.sqlite` 写入 ZIP；
5. 客户端读取 ZIP 并上传；
6. 服务器将上传内容写入临时文件；
7. 服务器解压 `parsed.sqlite`；
8. 服务器重新读取解压后的 `parsed.sqlite` 计算 SHA256；
9. 服务器逐个解压原始文件，再重新读取临时文件计算 SHA256；
10. 服务器复制整个同步包作为归档。

另外，服务器为每个原始文件重新打开一次 ZIP：

- `backend/sync/server.py:1096`

文件数量较少时影响有限，大量小文件时会放大开销。

### 5.6 缺少同步包生命周期管理

当前预览包、正式上传包、服务器拉取包和本地拉取缓存没有清晰的自动清理策略。大数据同步可能在客户端和服务器同时留下多份数据。

### 5.7 单体同步包缺少断点续传能力

当前以一个完整 `.fapkg` 文件作为上传单位。网络中断、服务器超时或导入失败时，可能重新生成和上传整个包。对于大数据在线同步，应支持对象级或分块级重试，并将上传与数据库导入解耦。

## 6. 跨客户端实体身份问题

### 6.1 适用范围和身份层次

本节的映射方案只解决多个客户端分别向同一服务器上传时的实体身份问题，不用于追踪客户端 A 通过离线包传给客户端 B 后的完整来源链。

需要区分四种概念：

- 本地数据库 `id`：只在当前 SQLite 或 MySQL 数据库内部有效；
- `client_uid`：客户端数据库中实体的稳定同步 UID，同一实体通过离线包在另一个客户端创建新记录时可以继承；
- `client_node_id`：本次向服务器上传的客户端节点 ID，即上传 manifest 顶层的 `source_node_id`；
- 服务器实体 ID：服务器中最终承载该实体的数字主键。

服务器处理客户端 B 的上传时，使用的是 B 的节点 ID 和 B 当前本地记录所持有的 `client_uid`。服务器不需要知道这条记录此前是否由客户端 A 的离线包导入。

不同客户端独立创建同一现实机型或飞机时，本地 `id` 和 `client_uid` 都不同，名称也可能不同。当前服务器匹配飞机主要依赖单个 `client_uid`，其次依赖同机型下的名称：

- `backend/sync/server.py:188`

如果首次上传时名称不同、架次没有重合、又没有现实世界的稳定飞机编号，系统没有足够信息判断两条飞机记录是同一架飞机。这个限制无法仅靠算法消除，只能允许先创建，再在出现证据后修复，或由用户人工合并。

### 6.2 `client_uid` 的生成和离线包传播规则

普通机型、飞机和架次在客户端首次创建时，由 SQLite 插入触发器生成 128 bit 随机 UID，当前格式为 32 个小写十六进制字符：

```sql
lower(hex(randomblob(16)))
```

- `backend/database.py:459`

目标方案保持这套生成机制不变，不需要修改触发器、UID 格式或普通业务创建流程：

- 普通本地创建仍然不传 `client_uid`，由现有触发器随机生成；
- 离线包导入并创建同一实体的新记录时，在 INSERT 中显式传入包内 `client_uid`；
- 现有触发器使用 `COALESCE(NEW.client_uid, lower(hex(randomblob(16))))`，因此会保留显式传入的 UID，只在 UID 为空时生成新值。

`client_uid` 一经确定，不应因名称、元数据、同步状态或服务器映射变化而修改。

离线包导入使用以下规则：

1. 包内实体在目标客户端不存在，需要创建新记录时，复制包内 `client_uid`。这表示同一实体沿 A -> B 的复制链继续使用同一个同步 UID。
2. 包内实体与目标客户端已有记录匹配时，保留目标记录原有 `client_uid`，只建立业务关联并按所选策略更新元数据。
3. 用户明确选择“复制为新的独立实体”时，生成新的 `client_uid`，避免后续服务器把副本错误识别为原实体。
4. 旧同步包没有 `client_uid` 时，目标客户端为新记录生成本地 UID。
5. 导入时如果相同 `client_uid` 对应的不可变结构、父实体关系或完整文件集合不一致，则停止并报告冲突，不能仅凭 UID 强制合并。

当前离线包导入新建机型、飞机和架次时只写入业务字段，没有复制包内 `client_uid`，随后由目标客户端触发器生成新 UID：

- `backend/sync/local_import.py:191`
- `backend/sync/local_import.py:211`
- `backend/sync/local_import.py:553`

这与上述目标规则不一致，但改动范围较小：只需要让这几处离线导入 INSERT 接受可选的包内 UID。创建同一实体的新记录时传入包内 UID；映射到已有记录时不执行 UID 更新。数据库表结构、随机 UID 生成触发器和普通本地创建逻辑均不需要修改。

示例：

```text
A 中飞机 UID = X

B 不存在该飞机：创建 B 记录并继承 UID X
B 已有同一飞机且 UID = Y：继续保留 Y
```

B 后续上传服务器时分别形成：

```text
(B, aircraft, X) -> server_aircraft_id
或
(B, aircraft, Y) -> server_aircraft_id
```

采用继承规则只能减少同一实体沿离线包复制时的 UID 分化。两个客户端独立创建同一现实实体时仍会产生不同 UID，仍需要结构、内容、重合架次或人工操作确定服务器映射。

预置机型必须在种子定义中携带显式、永久不变的 `client_uid`。同一预置机型在不同客户端和不同软件版本中都应保持该 UID，不应根据可编辑名称、别名、单位或完整配置动态变化。

当前 `backend/builtin_model_seeds.json` 中的 `500A` 已显式保存 `client_uid`，因此使用同一份种子文件的新客户端会创建出相同 UID。种子应用逻辑优先使用显式 UID：

- `backend/model_seeds.py:136`

如果种子没有显式 UID，当前代码会根据“名称 + 完整配置”计算 `builtin_` 哈希：

- `backend/model_seeds.py:24`

名称或配置变化会使该兜底 UID 变化；另外，如果客户端已经存在同名机型，种子逻辑会跳过创建，不会强制改写已有 UID。因此，配置哈希只作为旧种子兼容兜底，不能作为正式预置机型的长期身份规则。

### 6.3 使用服务器映射表缓存客户端身份

不为每种服务器实体增加多组客户端身份字段，而是在服务器增加一张通用映射表：

```sql
CREATE TABLE sync_entity_mappings (
    client_node_id    VARCHAR(64) NOT NULL,
    entity_type       VARCHAR(32) NOT NULL,
    client_entity_uid VARCHAR(64) NOT NULL,
    server_entity_id  BIGINT NOT NULL,
    matched_by        VARCHAR(32) NOT NULL,
    created_at        DATETIME(6) NOT NULL,
    updated_at        DATETIME(6) NOT NULL,
    PRIMARY KEY (client_node_id, entity_type, client_entity_uid)
);

CREATE INDEX idx_sync_entity_mapping_target
    ON sync_entity_mappings(entity_type, server_entity_id);
```

说明：

- `client_node_id` 使用上传 manifest 顶层的 `source_node_id`，表示当前向服务器同步的客户端；
- `entity_type` 第一版支持 `model`、`aircraft`、`flight`；
- `client_entity_uid` 使用该客户端当前本地实体的稳定 `client_uid`，不使用来源数据库的数字主键；
- `server_entity_id` 表示服务器目标实体 ID；
- `matched_by` 记录 `mapping`、`server_id`、`client_uid`、`structure`、`flight_overlap`、`content`、`name` 或 `manual` 等建立依据；
- 一条服务器实体可以被多个客户端节点和 UID 映射；
- 即使两个客户端因离线包传播而持有相同 `client_uid`，也分别写入各自节点下的映射；
- 客户端之间导入离线包时不写此表；
- 原始文件直接使用 SHA256 作为身份，不加入此表。

匹配流程应按以下顺序执行：

1. 优先查询 `(client_node_id, entity_type, client_entity_uid)` 映射；
2. 校验客户端已知的 `server_id`；
3. 如果其他客户端或服务器已有相同 `client_uid`，将其作为强匹配候选，但仍校验机型不可变结构、父实体关系或架次文件集合；
4. 再使用机型结构、架次内容、重合架次、名称或人工选择确定目标；
5. 一旦确定，在同一事务中写入或更新映射，后续同步不再重新猜测。

服务器实体表上的单个 `client_uid` 不能表达所有客户端别名，可以暂时保留为首个来源或兼容字段，但不能再作为完整身份集合，也不应在另一个客户端映射到该实体时被覆盖。服务器匹配的权威来源应逐步切换为 `sync_entity_mappings`。

`client_node_id` 参与长期映射主键，必须在客户端安装生命周期内保持稳定。第一版可以继续使用当前节点 ID 生成方式，避免扩大改动范围，但应避免节点 ID 在已有同步数据后被普通设置随意修改。升级为完整 UUID、以及把用户可编辑设备名称拆分为独立字段，可以作为后续兼容性加固，不作为本轮身份映射的前置条件。

### 6.4 机型按不可变结构匹配

机型可以按以下不可变内容生成确定性结构签名：

- `has_header`；
- `has_uav_send_id`；
- `extract_serial_from_path`；
- 数据类型 key；
- 文件匹配和解析规则；
- 原始列名；
- 列类型；
- 列顺序等解析结构信息。

以下可编辑展示信息不参与结构签名：

- 机型名称；
- 数据类型别名；
- 列别名；
- 单位；
- `scale_factor`。

当前 `config_signature` 对整个配置 JSON 计算哈希：

- `backend/server_database.py:606`

因此不能直接把包含别名和单位的完整配置签名当作机型身份。第一版可以在预检时临时计算结构签名，无需新增数据库字段；机型数量较少时，按现有注册表计算候选结构签名即可。

### 6.5 架次按完整原始文件集合匹配

架次内容身份可由排序后的原始文件多重集合计算：

```text
flight content identity =
    sorted[(data_type_key, sha256), ...]
```

比较时应保留条目数量，不能简单使用会丢失重复项的 `set`。原始文件名、存储路径、飞机名称、架次别名和飞行记录单不参与内容身份。

当前服务端 `flight_raw_files.sha256` 已有索引，因此第一版不必给 `flights` 表增加 `dataset_fingerprint` 字段。可以先用某个文件 SHA256 找候选架次，再比较完整文件集合。后续若性能证明动态计算过慢，再考虑缓存指纹。

### 6.6 通过重合架次推断飞机映射

对于来源飞机 A′ 下的一组架次：

1. 先按完整原始文件集合查找目标数据库中的已有架次；
2. 汇总这些已有架次所属的目标飞机；
3. 如果全部重合架次都指向同一目标飞机 A，则自动建立 A′ 到 A 的映射；
4. A′ 下未导入的其他架次也全部归入 A；
5. 已重合的架次只按元数据策略更新，不重复导入原始文件和解析数据；
6. 如果重合架次分别指向多个目标飞机，则停止并要求人工处理；
7. 如果没有任何重合架次，也没有已缓存映射，则首次上传只能创建新的目标飞机。

通过此规则建立映射后，应写入：

```text
(client_node_id, aircraft, client_aircraft_uid) -> server_aircraft_id
```

### 6.7 重复机型或飞机的修复

由于首次无证据时可能创建重复实体，系统需要提供最小合并能力，但不必第一版增加重定向表、合并历史表或大量状态字段。

合并应在单个事务中执行：

1. 选择要保留的目标实体，默认优先保留更早创建、已被更多来源映射引用的服务器实体；
2. 将 `sync_entity_mappings` 中指向重复实体的记录改为指向保留实体；
3. 迁移非重复架次；
4. 原始文件集合相同的架次只保留一份，并同步修正 `flight` 映射；
5. 如果遇到相同日期和 `session_key`、但原始文件集合不同的架次，则停止合并并要求人工处理；
6. 完成迁移后删除或软删除重复实体；
7. 当前同步响应返回新的目标 ID，写回发起客户端。

为了让未发起本次上传的其他客户端也能修正本地 `server_id`，拉取请求应通过协议字段 `source_node_id` 携带本地 `client_node_id`，服务器在拉取 manifest 中返回该节点相关的最新实体映射。本地应先应用映射，再处理实体新增、更新或删除。

### 6.8 当前机型展示元数据没有完整同步

本地修改列别名、单位或缩放系数时，只更新 `column_registry`，没有把所属机型标记为待同步：

- `backend/import_pipeline/format_configs.py:266`

修改数据类型别名也没有把所属机型标记为待同步：

- `backend/repositories/models.py:87`

服务器导入已有列时会直接跳过，不会更新已有列的别名和单位：

- `backend/sync/server.py:677`

因此需要把机型不可变结构和可编辑展示元数据分开处理。展示元数据修改后应进入上传队列；服务器应按明确的上传或拉取方向更新已有注册表记录，而不是只在记录不存在时插入。

### 6.9 当前版本冲突行为与目标覆盖规则不一致

当前服务器在发现服务器版本高于客户端已知版本时会返回 `server_changed_since_last_sync` 冲突：

- `backend/sync/server.py:321`
- `backend/sync/server.py:362`
- `backend/sync/server.py:411`

当前拉取预览遇到本地 `dirty` 实体时也会进入冲突：

- `backend/sync/local_import.py:1383`
- `backend/sync/local_import.py:1427`
- `backend/sync/local_import.py:1496`

根据已确认规则，应调整为：

- 用户明确选择上传时，本地元数据覆盖服务器；
- 用户明确选择拉取时，服务器元数据覆盖本地；
- UI 展示双方版本、更新时间和将被覆盖的字段摘要；
- 名称唯一性冲突、实体身份不确定、一个来源飞机映射到多个目标飞机等结构性问题仍必须阻断；
- 正式操作时重新预检，不能仅依赖之前的预览结果。

## 7. 性能改造方案

### 7.1 P0：先增加分阶段性能指标

当前只有同步运行总开始和结束时间，无法准确判断 54 秒服务器阶段和 49 秒本地阶段分别消耗在哪里。应先记录：

- manifest 生成耗时；
- `parsed.sqlite` 导出行数、字节数和耗时；
- 原始文件哈希耗时；
- 压缩耗时和压缩率；
- 上传字节数、耗时和平均吞吐量；
- 服务器接收和临时文件写入耗时；
- 解压及校验耗时；
- 每张解析表的 DELETE、INSERT 行数和耗时；
- 原始文件保存耗时；
- 数据库事务提交耗时；
- 拉取包生成、下载和本地导入耗时；
- 峰值内存和临时磁盘占用。

指标应写入结构化日志或 `sync_runs` 的阶段记录，前端展示真实阶段和字节进度，而不是只显示预设百分比。

### 7.2 P0：上传预览改为轻量 manifest

上传预览只生成轻量 manifest，不生成 `parsed.sqlite`，也不创建包含原始文件的 ZIP。

manifest 可以从本地数据库读取：

- 当前上传客户端的 `client_node_id`（协议字段 `source_node_id`）和各实体 `client_uid`；
- 机型不可变结构摘要及可编辑元数据；
- 飞机和架次元数据；
- 原始文件 SHA256、大小、数据类型和所属架次；
- 本地已知服务器 ID、版本和同步游标。

服务器返回：

- 实体映射和匹配依据；
- 将新增、覆盖或阻断的项目；
- 已存在的原始文件 SHA256；
- 正式上传真正缺少的数据范围；
- 将被覆盖的元数据摘要。

预览结果只是用户确认依据。正式上传开始时必须重新读取当前元数据、生成新的 manifest 并再次预检。如果预检结果与用户确认时发生实质变化，应要求重新确认，避免预览和正式提交之间的状态变化。

### 7.3 P0：大数据读写改为分批流式处理

需要改造的明确路径包括：

- 客户端生成裁剪后的解析数据；
- 服务端生成拉取解析数据；
- 本地导入拉取解析数据；
- 离线同步包导入。

建议：

- 每次读取 1000～10000 行；
- 读取一批立即写入目标格式；
- 写完释放该批对象；
- 批次大小根据行宽和可用内存测试；
- 大量 flight ID 分段查询，避免超长 `IN (...)`；
- 不在读出一批后再复制成多份完整 Python 列表；
- 分别测试窄表、宽表和大量小表。

服务端动态导入已经分批读取，优先通过指标优化批次大小和数据库写入方式，不重复改造已经存在的 `fetchmany()`。

### 7.4 P1：原始文件按 SHA256 内容寻址和增量上传

服务器预检按 SHA256 返回缺失文件列表。客户端只上传服务器尚不存在的原始文件。

建议存储逻辑：

```text
raw object key = sha256
flight_raw_files = 架次与 raw object 的关联、原始文件名和数据类型等元数据
```

收益：

- 天然去重；
- 同一架次重试时不重复上传已成功对象；
- 多个来源引用相同内容时只保存一次；
- 大文件可以独立分块和断点续传；
- 飞机、架次名称变化不再触发原始文件物理路径移动；
- 元数据同步与文件上传解耦。

原始文件存储受应用控制且内容不可变后，打包和预检可以信任数据库中保存的 SHA256，并通过大小等快速检查发现明显异常；服务端仍应在首次接收对象时边写入边计算完整哈希。

### 7.5 P1：支持上传会话、分块和断点续传

在线大数据同步建议改为上传会话：

1. 创建同步会话并提交正式 manifest；
2. 服务器完成身份匹配和正式预检；
3. 服务器返回缺失对象和已有分块状态；
4. 客户端上传缺失分块；
5. 服务端校验每块及完整对象哈希；
6. 客户端提交会话；
7. 服务器执行数据库导入；
8. 客户端等待或查询导入结果；
9. 成功后写回实体映射和服务器版本。

需要明确：

- 分块大小和块哈希；
- 重复、乱序和重叠分块处理；
- 会话过期和孤儿分块清理；
- 对象已上传但数据库导入失败时的重试；
- manifest 摘要与会话绑定；
- `session_id` 保证会话幂等，实体映射表保证跨客户端实体归属。

`run` 模式必须等待服务器导入提交成功并取得映射结果后再执行 pull，不能在异步导入尚未完成时直接拉取。

### 7.6 P1：同步包和缓存自动清理

建议区分：

- 用户主动导出的离线包：长期保留，由用户管理；
- 同步预览：改为内存中的轻量 manifest，不生成完整临时包；
- 自动上传临时文件：成功后删除，失败时有限期保留；
- 拉取缓存：导入成功后删除，或只保留最近少量记录；
- 服务器上传分块：会话完成或过期后清理；
- 服务器归档包：只有明确审计需求时保留，并设置保留周期和容量上限。

清理任务还应处理应用或服务器异常退出后遗留的过期临时文件。

### 7.7 P2：评估解析数据交换格式和数据库 bulk-load

不应在缺少阶段指标时直接确定 Parquet、Arrow 或 `LOAD DATA`。它们解决的问题不同：

- Parquet：列式压缩和批量读取；
- Arrow IPC：低开销序列化和系统间交换；
- CSV/TSV + MySQL `LOAD DATA LOCAL INFILE`：MySQL 批量导入通道；
- staging table：校验、映射、冲突处理和原子替换流程。

评估时必须覆盖当前动态表按架次先 DELETE 再 INSERT 的语义，并回答：

- staging table 如何按机型和数据类型创建；
- 动态列如何映射；
- 如何将来源 flight ID 转换为目标 flight ID；
- 导入失败如何回滚；
- 如何在事务中原子替换一个架次的解析数据；
- 是否仍需要可搬运的离线 `.fapkg`。

在线同步协议和离线包格式应分开：在线同步使用 manifest、内容对象和可恢复会话；离线 `.fapkg` 继续作为自包含、可人工搬运的交换格式。

## 8. 10GB 数据风险与容量定义

现有方案不建议直接用于 10GB 以上数据，但“10GB”本身不是充分的容量指标。测试集应同时描述：

- 原始文件总大小；
- 解析数据未压缩大小；
- 解析行数和平均列数；
- 架次数；
- 原始文件数量；
- 压缩后传输大小；
- 首次全量或日常增量；
- 重复对象比例；
- 网络环境。

现有结构性风险包括：

- 重复完整打包；
- 客户端导出、服务端拉取生成和本地导入的全量加载；
- 大量 ID、manifest 条目和 SQL 参数扩张；
- 服务器普通批量 INSERT 吞吐量可能不足；
- 客户端和服务器需要多份临时磁盘空间；
- 失败后缺少断点续传；
- 多客户端身份不正确时可能产生重复机型、飞机和架次。

具体耗时不能只使用一次样本进行线性外推，应在完成阶段指标后建立容量模型。

## 9. 推荐实施顺序

### 第一阶段：身份正确性与同步语义

1. 在服务器增加 `sync_entity_mappings`，客户端上传时按 `(client_node_id, entity_type, client_entity_uid)` 查询和写入映射。
2. 保证现有节点 ID 在已有同步数据后保持稳定；完整 UUID 和独立设备名称作为后续兼容性加固。
3. 离线包导入实现“新建继承包内 UID、匹配已有保留目标 UID、复制为独立实体生成新 UID”的规则。
4. 所有正式预置机型使用显式、永久不变的 `client_uid`。
5. 所有服务器实体匹配优先查询映射表，相同 `client_uid` 跨节点只作为需校验的强候选。
6. 实现机型不可变结构签名，排除名称、别名、单位和展示缩放系数。
7. 架次按完整原始文件集合查重。
8. 通过重合架次自动建立飞机映射。
9. 增加最小的重复机型、飞机合并预检和事务合并能力。
10. 修复数据类型别名、列别名和单位没有进入同步队列的问题。
11. 在线同步改为用户选择方向决定元数据覆盖。
12. 离线包增加 `package_wins` / `target_wins` 整包策略。

预期结果：多客户端名称和本地 ID 不同也不会重复导入已有架次；无法首次判断的实体可以在后续出现重合证据后修复。

### 第二阶段：快速性能收益

1. 增加服务器和本地导入的分阶段指标。
2. 上传预览改为轻量 manifest，取消预览完整打包。
3. 客户端导出、服务端拉取生成和本地导入改为流式分批。
4. 大量 ID 查询分段或改用临时选择表。
5. 自动清理临时包和拉取缓存。

预期结果：减少一次完整打包，降低大表内存峰值，并准确识别剩余瓶颈。

### 第三阶段：大数据传输能力

1. 原始文件改为 SHA256 内容寻址。
2. 预检返回服务器缺失对象列表。
3. 引入上传会话、分块上传和断点续传。
4. 上传与数据库导入解耦，但 `run` 等待导入成功后再 pull。
5. 增加会话、分块和孤儿对象清理。

预期结果：失败重试不再重新上传全部数据，重复对象不再重复传输。

### 第四阶段：解析数据批量导入

1. 根据实测比较优化后的批量 INSERT、Parquet/Arrow 和 MySQL bulk-load。
2. 如有必要，建立 staging table 和原子替换流程。
3. 对 1GB、5GB、10GB、20GB 目标负载进行容量测试。

预期结果：降低数百万至数千万解析行的导入时间，并形成可验证的容量边界。

## 10. 验收建议

### 10.1 身份与覆盖规则

- 两个客户端使用不同名称创建结构相同的机型，能够映射到同一目标机型；
- 同一实体通过离线包在目标客户端新建时继承 `client_uid`；
- 离线包实体映射到目标客户端已有记录时不覆盖目标 `client_uid`；
- 用户把包内实体复制为独立实体时生成新的 `client_uid`；
- 同一预置机型在不同客户端和不同软件版本中保持显式固定 `client_uid`；
- 相同 `client_uid` 但不可变结构、父实体关系或完整文件集合不一致时阻断；
- 两个客户端使用不同飞机名称，但存在一个重合架次时，剩余新架次自动归入同一目标飞机；
- 相同原始文件集合不允许生成第二个架次；
- 首次没有重合架次时允许分别创建，后续出现重合证据时可以事务合并；
- 一个来源飞机的重合架次指向多个目标飞机时阻断；
- 合并遇到相同日期和 `session_key`、但文件集合不同时阻断；
- 上传以本地元数据覆盖服务器；
- 拉取以服务器元数据覆盖本地；
- 离线包 `package_wins` 和 `target_wins` 行为符合定义；
- 名称覆盖撞到另一个不同实体时阻断；
- 其他客户端拉取后能够更新合并后的目标 ID。

### 10.2 性能与可靠性

- 1GB、5GB、10GB、20GB 分级数据集；
- 大文件和大量小文件两种组合；
- 首次全量同步和第二次无变化同步；
- 少量文件变化的增量同步；
- 上传中断后的断点续传；
- 导入失败后的幂等重试；
- 客户端和服务器磁盘不足；
- 客户端内存峰值；
- 服务端数据库写入吞吐量；
- 同步期间客户端和服务器重启；
- 临时文件和过期会话清理。

建议定义明确目标，例如：

- 无变化同步只交换轻量 manifest，并在数秒内完成；
- 已上传对象不重复传输；
- 10GB 上传失败后只重传未完成分块；
- 动态数据处理内存峰值受批次大小约束，不随单表总行数线性增长；
- 前端显示真实上传速率、已完成字节数和服务器导入阶段；
- 任何相同原始文件集合都不会产生重复架次。

## 11. 当前结论

当前约 3 分钟等待由预览重复打包、正式打包、服务器处理、拉取包生成和本地导入等多个阶段叠加产生。重复打包是明确且容易消除的问题，但并不是本次 160 秒等待中的最大部分；应先补充分阶段指标，再决定数据库导入格式。

在性能改造之前，还必须补齐多个客户端上传同一服务器时的实体身份：本地数字 ID 和服务器实体表上的单个 `client_uid` 无法表达多个客户端对应同一目标机型或飞机。第一版只在服务器使用一张通用 `sync_entity_mappings` 表即可，不要求客户端之间的离线包导入维护同一映射表。离线包在目标客户端新建同一实体时继承包内 `client_uid`，匹配已有实体时保留目标 UID；机型通过不可变结构匹配，架次通过完整原始文件集合匹配，飞机通过重合架次建立服务器映射；首次无证据时允许创建，后续通过自动或人工合并修复。

推荐优先完成：

1. 服务器通用实体映射、离线包 UID 传播规则、固定预置 UID、机型结构匹配、架次内容查重和飞机合并；
2. 在线上传/拉取与离线包导入的明确元数据覆盖规则；
3. 分阶段性能指标、轻量预览和流式分批；
4. 内容寻址、分块上传和断点续传；
5. 根据实测选择解析数据批量导入方案。

完成身份正确性和第一轮性能改造后，再通过目标负载测试决定是否升级为 Parquet/Arrow 加数据库 bulk-load。
