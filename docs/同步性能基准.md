# 同步解析数据导入基准

## 1. 目的

本报告记录第四阶段解析数据导入方案的可复现实测。基准工具位于
`script/benchmark_sync_import.py`，只创建随机命名的 `sync_benchmark_*` 表，
每轮结束后删除，不读写业务表。工具必须显式传入 `--confirm-write`。

## 2. 测试环境

- Windows 10；
- Python 3.12.3；
- MySQL 8.0.27；
- SQLAlchemy 2 + PyMySQL；
- 动态表包含生产路径相同的 `(flight_id, time_sec)` 和 `flight_id` 索引；
- MySQL `@@local_infile = 0`。

结果 JSON 保存在本地忽略目录 `.devdata/`，不提交机器和路径相关数据。

## 3. 批量 INSERT

### 3.1 窄表

工作负载为 50,000 行、8 个数值列，每个批次大小运行三轮并取中位数。

| 批次行数 | 中位吞吐（行/秒） | 最低 | 最高 |
| ---: | ---: | ---: | ---: |
| 250 | 14,543 | 14,240 | 14,714 |
| 500 | 14,725 | 14,667 | 14,859 |
| 1,000 | 14,776 | 14,091 | 14,853 |
| 5,000 | 6,155 | 4,381 | 15,111 |

窄表在 250 至 1,000 行范围内差异很小；5,000 行波动明显，不适合作为默认值。

### 3.2 宽表

工作负载为 20,000 行、92 个数值列，接近项目当前最宽动态表。

| 批次行数 | 中位吞吐（行/秒） | 最低 | 最高 |
| ---: | ---: | ---: | ---: |
| 100 | 2,406 | 2,398 | 2,409 |
| 250 | 1,192 | 1,165 | 2,329 |
| 500 | 1,803 | 1,788 | 2,337 |
| 1,000 | 1,358 | 1,219 | 1,402 |

宽表使用 1,000 行批次会构造接近十万个 Python/SQL 参数，吞吐和内存都差于
100 行批次。因此服务端不再使用固定批次，改为：

```text
batch_rows = clamp(10000 / column_count, 100, 1000)
```

复测结果：11 列取 909 行时约 14,929 行/秒；95 列取 105 行时约 2,407 行/秒。

## 4. Arrow、Parquet 与 bulk-load

Arrow IPC 和 Parquet 使用可选的 PyArrow 25 测试，不加入生产依赖。

| 工作负载 | 格式 | 大小 | 编码行/秒 | 解码行/秒 |
| --- | --- | ---: | ---: | ---: |
| 50,000 行，8 数值列 | Arrow IPC | 5.40 MB | 132,056 | 17,152,659 |
| 50,000 行，8 数值列 | Parquet/Zstd | 1.44 MB | 119,794 | 4,668,752 |
| 20,000 行，92 数值列 | Arrow IPC | 15.70 MB | 23,917 | 3,214,194 |
| 20,000 行，92 数值列 | Parquet/Zstd | 6.45 MB | 15,617 | 518,231 |

这两个格式的编解码不是当前 MySQL 写入瓶颈的替代通道。MySQL 不能直接载入
Arrow 或 Parquet，解码后仍要执行 INSERT，或者再次转成文本供 bulk-load 使用。
当前在线协议还要兼容离线 SQLite 包，引入新格式会增加依赖和转换步骤，暂不采用。

`LOAD DATA LOCAL INFILE` 在客户端连接已启用的情况下仍被服务器以错误 3948 拒绝，
因为当前部署的 `@@local_infile` 为 0。基准工具会把该方法报告为 `unavailable`，
不会修改 MySQL 全局安全设置。没有可用且已测量的 bulk-load 通道，因此本阶段不增加
staging table；现有 InnoDB 事务中的 DELETE + INSERT 已提供失败回滚和原子替换。

## 5. 容量档位

工具支持 `--target-gb`，按指定 TSV 有效载荷估算行数并执行真实 MySQL 写入。
启动前会检查临时目录至少有目标大小的 1.2 倍空间，并在 MySQL datadir 位于本机时
检查至少 3 倍空间。空间不足默认拒绝运行。

当前合成行宽对应的容量矩阵为：

| TSV 有效载荷 | 8 数值列 | 92 数值列 |
| ---: | ---: | ---: |
| 1 GB | 14,717,058 行 | 1,747,300 行 |
| 5 GB | 73,585,290 行 | 8,736,499 行 |
| 10 GB | 147,170,579 行 | 17,472,997 行 |
| 20 GB | 294,341,158 行 | 34,945,993 行 |

示例：

```powershell
.venv\Scripts\python.exe script\benchmark_sync_import.py `
  --target-gb 1 --value-columns 92 --batch-sizes 105 `
  --trials 1 --skip-load-data --confirm-write `
  --output .devdata\sync_capacity_wide_1gb.json
```

按本次代表性吞吐做单纯 INSERT 外推，1 GB 约需 12 至 16 分钟，20 GB 约需
4 至 5.5 小时；这只是容量测试排期参考，不是端到端 SLA。原始对象比例、SQLite
大小、索引页、事务日志、网络和磁盘都会改变结果。

当前已验证的是 50,000 行窄表、20,000 行宽表和项目约 201 MB 本地数据库的日常
路径。1/5/10/20 GB 端到端矩阵尚未执行，不能标记为已通过。执行完整矩阵前需要：

本机只读容量预检结果为：1 GB、5 GB、10 GB 通过空间检查；20 GB 未通过。
20 GB 档位要求 MySQL datadir 至少保留约 64.4 GB，实测仅约 53.6 GB 可用，
因此工具没有启动写入。该结果是当前测试机的明确空间边界，不代表协议的理论上限。

1. 为测试机预留 MySQL 数据、索引、事务日志和临时对象空间；
2. 固定网络、MySQL 配置和数据形状；
3. 同时记录原始文件字节、解析字节、行数、列宽、文件数和重复对象比例；
4. 验证中断恢复、磁盘不足和服务重启，不只记录成功路径耗时。
