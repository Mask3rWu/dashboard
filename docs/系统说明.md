# Flight Analyzer 系统架构说明

> 本文档面向后续开发人员，描述 Flight Analyzer 的整体架构、各子系统职责、数据模型与关键设计约定。
> 配合使用说明 [`introduce.md`](./introduce.md) 和科研网部署 [`RESEARCH_NETWORK_SETUP.md`](./RESEARCH_NETWORK_SETUP.md) 阅读。

---

## 1. 项目概述

Flight Analyzer 是一套飞行数据分析应用，用于把外场采集的飞行数据文件导入、组织、分析，并在科研网内多节点间同步。

整体由三部分构成：

- **FastAPI 后端**：业务逻辑、数据持久化、同步编排。
- **React 前端**：单页应用，构建产物由后端以静态文件方式托管。
- **pywebview 桌面壳**：把后端 + 前端封装成桌面应用。

系统存在**两套部署形态**，通过中立的同步包通信，互不直连对方数据库：

| 形态 | 入口 | 数据库 | 监听 | 用途 |
|---|---|---|---|---|
| 本地桌面端 | `main.py` | 本机 SQLite | `127.0.0.1:18520~18529` | 外场/科研网客户端，导入、分析、本地缓存 |
| 协作服务器端 | `server_main.py` → `server_app.py` | MySQL | `0.0.0.0:9000` | 科研网统一服务器，权威数据源，无 GUI、无前端 |

两端**复用同一份 `backend/` 代码包**，但选用不同子模块（本地用 SQLite 系列，服务器用 MySQL 系列）。

### 技术栈

- **后端**：Python、FastAPI、uvicorn、SQLite（本地）、SQLAlchemy + pymysql（服务器）、pywebview、PyInstaller
- **前端**：React 19、TypeScript、Vite 8、Tailwind CSS 4、ECharts 6（`echarts` + `echarts-for-react`）、lucide-react
- **打包**：PyInstaller 单文件 EXE（Windows），产物 `packaging/dist/FlightAnalyzer.exe`

## 4. 数据模型与数据库

### 4.1 双数据库边界

- **本地 SQLite**：便携、离线、文件型，`%APPDATA%/FlightAnalyzer/data.db`。既存服务器数据的缓存，又存本地新数据和同步状态机。`DB_BACKEND` 目前只实现 `sqlite`，非 sqlite 会启动失败——它是为未来切换预留的开关，repository 层是替换边界。
- **服务器 MySQL**：多客户端并发、事务、外键约束、全局变更日志，是权威源。连接串由 `flight_analyzer.ini` 的 `[mysql]` 段构造。

Schema 版本号（**修改 schema 必须同步以下常量**）：

| 常量 | 值 | 位置 |
|---|---|---|
| `CURRENT_SCHEMA_VERSION` | `4` | `backend/database.py` |
| `PACKAGE_VERSION` | `2` | `backend/sync/protocol.py` |
| `SYNC_PROTOCOL_VERSION` | `1` | `backend/sync/protocol.py` |

### 4.2 本地 SQLite 核心表

| 表 | 用途 |
|---|---|
| `schema_version` | schema 版本追踪 |
| `app_settings` | 键值运行时设置（`local_node_id`、`node_id`、`server_base_url`、`last_pull_cursor` 等） |
| `users` / `auth_sessions` | 本地用户缓存 + bearer session（仅存 token 的 sha256 摘要） |
| `aircraft_models` | 机型 |
| `aircraft` | 飞机（挂在机型下） |
| `flights` | 飞行架次 + 人工记录字段（`record_*`） |
| `data_table_registry` | 机型 × data_type → 动态表名映射 |
| `column_registry` | 每个机型每列的元数据（label/unit/ordinal/scale_factor/is_numeric） |
| `presets` / `filter_presets` | 列选择预设 / 筛选预设（按机型作用域） |
| `flight_raw_files` | 架次关联的原始文件元数据 |
| `sync_imports` | 同步包导入报告 |
| `sync_runs` | 同步运行记录（push/pull/full） |
| `model_{model_id}_{data_type_key}_data` | **动态数据表**，存解析后的时序数据 |

**同步状态列**（`SYNC_COLUMNS`）：`client_uid`、`server_id`、`source_node_id`、`sync_origin`、`sync_state`、`server_version`、`last_sync_at`、`sync_error_json`、`updated_at`、`deleted_at`、`server_deleted_at`。`aircraft_models`/`aircraft`/`flights`/`flight_raw_files`/`sync_imports` 都带这套字段。

### 4.3 动态数据表

每种机型 × 数据类型对应一张动态表，表名由 `format_configs.data_table_name(model_id, data_type_key)` 生成：

```text
model_{model_id}_{data_type_key}_data
```

固定列：`id`、`flight_id`（FK flights ON DELETE CASCADE）、`time_str`、`time_sec`，加上配置列。索引 `idx_m{model_id}_{dt_key}_ft` on `(flight_id, time_sec)`。

> **禁止硬编码表名**——所有动态表名必须通过 `data_table_name()` 生成。

### 4.4 服务器 MySQL 差异

服务器无 `sync_state`/`sync_origin` 等本地状态字段，但每实体带：
- `version`：乐观锁，每次更新 +1
- `deleted_at`/`deleted_by`/`delete_reason`：软删除
- 额外表：
  - `sync_changes`：全局变更日志，`cursor` BIGINT 自增，是 pull 增量的源头
  - `sync_clients`：节点最后见面/游标
  - `sync_imports`：按 `package_id + source_node_id` 幂等去重
- 动态数据表名：`server_data_m{model_id}_{data_type_key}`，列类型映射 MySQL（REAL/FLOAT/DOUBLE→DOUBLE，INT/BOOL→BIGINT，TEXT→TEXT）

### 4.5 去重与唯一性边界

- **架次去重**：`flights` 的 `UNIQUE(aircraft_id, flight_date, session_key)`。`source_path` 仅作 provenance，不参与去重（文件夹可移动后重新导入）。
- **原始文件去重**：`flight_raw_files` 的 `UNIQUE(flight_id, storage_rel_path)`，物理存储按 sha256 校验。
- **跨环境实体匹配**：优先 `client_uid`（客户端生成的全局唯一 ID），其次 `name`，最后业务键。

## 5. 后端子系统详解

### 5.1 导入流水线

把外部飞行数据文件夹导入数据库，建立"机型 → 飞机 → 飞行架次"层级，同时转存原始文件。

#### 模块职责

| 模块 | 职责 |
|---|---|
| `import_pipeline/scanner.py` | 目录扫描、文件类型识别、session_key 时间聚类、机型自动匹配预览、FlightRecord XML 解析。**纯读，不落库**。 |
| `import_pipeline/format_configs.py` | 机型/数据表/列注册表 CRUD、动态建表 SQL、`generate_config_from_scan`（自动生成配置）、`compare_configs`（机型匹配打分）。 |
| `import_pipeline/parser.py` | 单次 session 导入的**编排入口** `import_session()`，协调各模块完成一次入库事务。 |
| `import_pipeline/importer.py` | 配置驱动的通用导入器：按 `column_registry` 的 ordinal 读 TSV 行、类型强转、批量 INSERT 到动态表，回写架次起止时间/时长/行数。 |
| `raw_storage.py` | 原始文件归档：sha256 校验复制到可读路径、路径刷新（机型/飞机改名后搬文件）、logical manifest 生成。 |
| `model_seeds.py` | 内置机型种子应用到本地 SQLite 和服务器 MySQL。 |

#### 端到端数据流

**A. 扫描预览** (`POST /api/flights/scan` → `import_pipeline.scanner.scan_folder_sessions`)

1. **路径校验**：要求路径中存在以 8 位 `YYYYMMDD` 开头的目录，否则报错。
2. **机型匹配**：`generate_config_from_scan` 从文件夹生成配置 → `compare_configs` 对所有已存机型打分 → 最高分 ≥ `MATCH_THRESHOLD = 0.95` 则用该机型，否则标记 `is_new=True` 引导用户新建。
3. **递归扫文件**：`os.walk` 找所有 `.txt`，用 `get_data_type_key`（正则匹配）分类，从路径提取飞机序号。
4. **session 聚类**：按 session_key 的 `HHMMSS` 前缀换算午夜秒数，3 秒内合并为一场次；带 `_`（有序号）的 key 优先作 canonical key。
5. **FlightRecord XML**：在文件目录下找 `FlightRecord_<session_key>.xml`，按别名映射到 `record_*` 字段作表单默认值。
6. **去重标记**：按 `model_id + flight_date + session_key` 查重，已导入标 `imported`，撞到其他飞机填 `conflicting_aircraft`。

**B. 导入落库** (`POST /api/flights/import` → `parser.import_session`)

1. 校验路径 + 取 `model_id` + 加载该机型建表时存的 config（**不复扫**，复用 stored config）。
2. 重扫 + 按目标飞机序号过滤 + 定位目标 cluster。
3. 提取日期 + `find_duplicate_flight` 查重，命中则拒绝。
4. `insert_flight` 写 flights 行（含手填 `record_*`）。
5. `importer.import_files_for_session`：每个文件按 `is_alert` 分流（告警合并描述 / 数据按 ordinal 取 token 强转入库）；修复整秒重复；回写架次起止时间/时长/行数。
6. `raw_storage.attach_raw_files_to_flight`：sha256 校验 + 原子复制到可读路径 + 写 `flight_raw_files`。
7. 有警告则写 `flights.raw_import_warnings`（JSON）。
8. `conn.commit()`；任一步异常 `conn.rollback()`。

#### 关键概念

- **`data_type_key`**：由文件名 pattern 经 `_sanitize_data_type_key` 派生（小写化、非 `\w` 替 `_`），是注册表/动态表名/文件分类的共同主键，全链路贯穿。
- **`session_key`**：文件名中类型 marker 之后的时间戳片段，通常 `HHMMSS[_seq]`。
- **"所有 .txt 平等"原则**：无硬编码数据类型白名单。未知类型与已知类型同等处理；`is_alert` 由文件名含 `alert` 推导，`is_raw`（原始字节转储）由内容分析（hex 占比）推导。
- **stored config 单一真相源**：导入复用建机型时存的 config，用户取消勾选的 raw 类型在扫描阶段即被跳过。

#### 原始文件归档策略

- **可读路径优先，非 sha256 哈希路径**。物理路径：`DATA_DIR/raw_files/机型_{model_name}_{model_id}/飞机_{aircraft_name}_{aircraft_id}/{原始相对路径}`，文件名加 `YYYYMMDD_` 前缀。若原始相对路径首层就是飞机名称，则去掉该重复层；`ParserData` 等后续目录保持不变。因此选择日期目录或其下的飞机目录导入时，会得到一致的转存路径。
- sha256 仅作**校验和去重键**，不作寻址。`_copy_verified` 先复制到临时文件、重算 hash 比对、再 `os.replace` 原子替换。
- 机型/飞机改名后，`refresh_raw_storage_paths` 把已存原始文件搬到新业务名路径。
- `raw_import_warnings`：归档过程中失败的文件列表（hash mismatch / IO 错 / 路径逃逸），JSON 存于 `flights.raw_import_warnings`，前端展示。

#### 事务边界

- **`parser.import_session` 是唯一的跨模块大事务**：insert_flight → import_files → attach_raw_files → 写警告 → commit；异常 rollback。
- `importer._batch_insert` / `import_files_for_session` 不 commit（注释明确 caller 持有事务）。
- `format_configs.register_model_tables` 默认 `commit=True`，但被 `model_seeds` 调用时传 `commit=False` 交给初始化流程。
- `update_column_metadata` 自管小事务。

### 5.2 同步子系统

本地 SQLite 客户端 ↔ 服务器 MySQL 之间的数据同步，是系统最复杂的子系统。

#### 三种同步模式（编排位于 `backend/sync/workflow.py`）

- **push**（`POST /api/sync/push`）：本地选中项 → 导出 `push_batch` 包 → 服务器预检 → 冲突则标记结束 → 上传 → 服务器导入 → 写回本地 `server_id/server_version`，置 `synced`。
- **pull**（`POST /api/sync/pull`）：读 `last_pull_cursor` → 拉轻量清单 → 本地预判每条是 `metadata`（只更元数据）还是 `bundle`（需下载）→ 下载导入 → 推进游标。
- **run**（`POST /api/sync/run`）：先 push 队列中所有待上传项，再 pull（带 `exclude_source_node_id=local_node_id` 避免拉回自己刚推的数据）。即"同步一次 = push 后 pull"。

另有 `manual_export` 包类型，用于离线节点间互导，不经服务器，需人工确认机型/飞机映射。

#### .fapkg 包结构

`.fapkg` 本质是 zip，由 `sync.package.export_package` 或 `sync.server.build_pull_bundle` 生成：

```text
manifest.json              跨环境契约（见下）
data/parsed.sqlite         裁剪过的解析数据缓存（表用 source_id 保留源端主键，外键改名解耦主键空间）
raw_files/<rel_path>       原始文件对象（按 sha256+size 校验）
models/model_<id>.json     机型列定义配置
```

**manifest 作为跨环境契约**：两端 schema 不同（SQLite vs MySQL），manifest 是两边都能解析、校验、对齐的唯一中立表示。`validate_manifest` 强制 `package_version>=2` 且 `sync_protocol_version==1`；`parsed_data` 的 sha256/size 解包时重算比对；`schema_version` 不一致则走"原始文件重解析"路径。包内路径必须是相对路径，禁止绝对路径与 `..`。

#### 同步状态机 `sync_state`

本地 `aircraft_models`/`aircraft`/`flights`/`flight_raw_files` 都有 `sync_state`：

| 状态 | 含义 |
|---|---|
| `local_only` | 仅本地存在（原始文件默认值） |
| `pending_upload` | 待上传（机型/飞机/架次默认值） |
| `dirty` | 本地已修改、与服务器版本不一致，需重传 |
| `upload_failed` | 上传失败 |
| `conflict` | 冲突，待人工处理 |
| `synced` | 已与服务器同步 |
| `server_cache` | 服务器数据的本地缓存（本地未改动） |
| `server_deleted` | 服务器已软删除，本地保留墓碑 |

流转：新建 → `pending_upload`/`local_only`；push 成功 → `synced`；push 失败 → `upload_failed`；冲突 → `conflict`；pull 拉到新数据 → `server_cache`（已 `synced` 的保持）；pull 遇服务器删除且本地非 dirty → `server_deleted`，本地 dirty → `conflict`。

`UPLOAD_QUEUE_STATES = (local_only, pending_upload, dirty, upload_failed)` 定义可上传集合。

#### 同步标识体系

| 标识 | 作用 |
|---|---|
| `client_uid` | 客户端为每条记录生成的全局唯一 ID，**跨环境匹配同一实体的首选键** |
| `server_id` | 服务器主键，push 成功后写回本地；pull 时反向匹配本地缓存 |
| `source_node_id` | 数据 originating 节点（如 `node-xxxxxxxx`），标记来源；pull 时 `exclude_source_node_id` 跳过自己刚推的数据 |
| `server_version` | 服务器乐观锁版本，preflight 比对以检测 `server_changed_since_last_sync` 冲突 |
| `last_pull_cursor` | 本地 `app_settings` 中已拉取到的服务器 `sync_changes.cursor` 位置，pull 增量基于它 |

#### push 流程

1. `export_package(bundle_kind="push_batch")` 生成包，写入 `base_server_cursor = last_pull_cursor`。
2. `sync.client.preflight` → 服务器 `build_preflight_plan`：按 `client_uid → name → 业务键` 逐条匹配，判定 create/existing/update_metadata/conflict/restore，返回冲突与 `needs_pull`。先查 `sync_imports` 幂等（同 `package_id+source_node_id` 已导入则返回旧报告）。
3. 冲突则 `mark_conflict` 结束。
4. `sync.client.push_bundle`（multipart 流式上传，字节级进度回调）→ 服务器 `import_push_bundle`：解包重算 hash → 再 preflight → upsert 实体（version+1 + 写 sync_changes）→ 校验归档原始文件 → 解析数据批量写动态表（先 DELETE 同 flight 旧行再插）→ 写 sync_imports → **commit 后返回**（保证客户端紧接的 pull 能看到）。
5. `apply_push_report` 按 mappings 写回本地 `server_id/server_version/sync_state='synced'`。

#### pull 流程

1. 读 `last_pull_cursor`。
2. `sync.client.pull_preview` → 服务器 `build_pull_preview`：基于 `sync_changes.cursor > since` 聚合变更并向上展开依赖（model→aircraft→flight），返回轻量清单（不含 parsed 数据）。
3. 本地 `preview_pull_manifest` 预判每条 `transfer_kind`：本地已有且原始文件 sha256 集合是服务器子集 → `metadata`（无需下载），否则 `bundle`。
4. 全 metadata → `apply_pull_manifest_metadata` 只更元数据 + 推进游标；否则 `download_bundle` → `import_pull_bundle`。
5. `import_pull_bundle`：upsert 机型/飞机/架次（处理 dirty/server_deleted/业务键冲突，可应用 `flight_resolutions`）→ 导入原始文件 → DELETE 旧行后批量重插解析数据 → 推进游标。

#### 冲突检测与解决

**冲突类型**：
- push 侧（服务器 preflight）：`model_name_config_mismatch`、`server_changed_since_last_sync`、`model_name_conflict`/`aircraft_name_conflict`、`business_key_raw_hash_mismatch`。
- pull 侧（本地）：`dirty_flight`/`dirty_model`/`dirty_aircraft`、`server_deleted_dirty_local`、`business_key_conflict`、`local_unsynced_business_key_conflict`。

**标记**：`sync_state='conflict'` + `sync_error_json`（含 phase/reason/相关 server_id）。

**解决路径**：
- push 侧冲突：本地调整（改名/接受服务器版本）后重新 push。
- pull 侧冲突：`import_pull_bundle` 的 `options.flight_resolutions[server_id]` 传 `"local"`（保留本地）或 `"server"`（采用服务器）；不传则留 `conflict` 待人工。pull 预览端点会先列出所有冲突供前端展示。

#### runtime_context

`runtime_context.runtime_context(conn, server_token)` 聚合前端运行时状态条所需信息：`data_dir`、`server_base_url`、`server_reachable`/`server_status`（online/offline/not_configured）、`local_node_id`、`server_user`/`server_capabilities`、`sync_summary`（待传/失败/冲突计数 + 最近 push/pull 时间）。服务器探活 `/health`（2 秒超时）。

> **environment**（`research`/`field`）由 `permissions.get_app_context` 维护，存 `app_settings`，决定默认 node_id 前缀和导出包的 `source_environment`。
> **login_mode**（`online`/`offline`）由 `backend/api/desktop/routers/auth.py` 的登录端点决定。

### 5.3 认证与权限

#### 登录双模式（`POST /api/auth/login`）

1. 取 `server_base_url`。若已配置 → 尝试 **online**：`sync.client.login(server_base_url, username, password, timeout=5)`。
   - 成功：用服务器返回的 user 信息经 `upsert_user_cache` 写本地 `users` 表——**密码用本应用自己的 PBKDF2 重新哈希**（不是服务器哈希），便于下次离线登录。建本地 session。返回 `token`（本地）+ `server_token`（服务器）+ `login_mode: "online"`。
   - 抛 `SyncClientError`：状态码 400/401/403（凭据问题）→ 直接透传；其它（网络/5xx）→ 记 `online_error`，**降级 offline**。
2. **offline**：取本地缓存行 `verify_password` 校验。失败抛 401（若有 online_error 合并提示）。成功返回 `login_mode: "offline"`。

即：online 优先、网络故障自动回退本地缓存账号；凭据错误不回退。online 登录会刷新本地用户缓存，从而支持后续离线登录。

#### Session token 机制

- `secrets.token_urlsafe(32)` 生成原始 token，库中只存 `sha256(token)` 摘要；`expires_at = utcnow + 7 天`。
- 校验：bearer token → `sha256` → 联表 `auth_sessions JOIN users`，带过期判断。
- 改密会吊销该用户全部会话；token 字符串从未落盘，丢失只能重登。

#### RBAC 能力体系

```text
ALL_CAPABILITIES = {manage_users, change_own_password, delete_models,
                    delete_aircraft, delete_flights, update_columns}
角色：admin / user
```

- 未登录 → `[]`
- 任意已登录用户 → 基础 `{change_own_password}`
- `admin` → 额外并入 `{manage_users, delete_models, delete_aircraft, delete_flights, update_columns}`

`require_capability(conn, request, capability)` 是守卫函数，不满足抛 403。能力列表随 `/api/auth/me`、登录响应下发给前端，前端据此显隐菜单/按钮。

> 当前能力体系是**纯角色驱动**的静态映射，`context.environment` 尚未参与权限判定，预留了扩展点。

#### 服务器用户管理 vs 本地用户缓存

- **服务器用户管理**（`/api/users` 系列）：纯透传到 `sync.client` 再到中心服务器，**不写本地库**。要求请求带服务器 admin token。
- **本地用户缓存**（`users` 表）：online 登录时 `upsert_user_cache` 写入 + `ensure_builtin_admin` 建的内置 admin（`admin / 123456`）。仅供 offline 登录校验和本地会话，无面向用户的本地用户 CRUD 路由。

### 5.4 数据分析（`analysis.py`）

基于 `column_registry` + `data_table_registry` 双注册表，**类型无关**——对任意 `.txt` 派生的数据类型一视同仁，不再硬编码表名/列名。

| 函数 | 职责 |
|---|---|
| `get_aligned_data` | **核心**：多列对齐到统一 1 秒网格，输出曲线 + 告警 |
| `apply_filter` | 对对齐结果做条件过滤，产出 mask 与连续段 |
| `get_flight_stats` | 飞行级元数据（时长、起止、无人机名） |
| `get_correlation` | Pearson 相关性矩阵 |
| `get_anomalies` | 滑动窗口 z-score 异常检测（`window_size=30, sigma=3.0`） |
| `get_compare` | 多飞行单列对比 |
| `get_columns_for_flight_api` | 该飞行实际有数据的可用列（委托 `format_configs`） |

**对齐算法要点**：
- `_generate_flight_grid` 生成覆盖全飞行的统一 1 秒网格，起点取所有数据表与飞行元数据的最早时间。
- 多行/秒的 `high_rate` 表：游标下采样，取每秒首行。
- 低频表：二分最近邻（规则序列容差 0.05s，不规则 1.0s）。
- 告警表按 `is_alert` 标志位定位，列按 `ordinal` 取，启发式选 desc/extra 列。

> **`scale_factor`** 仅作元数据透传返回前端，`analysis.py` 内**不对 values 做缩放**——分析计算始终基于原始值，缩放展示交给前端。过滤发生在对齐之后，引用的是对齐后的 1Hz 序列。`preset` 概念不在本模块，由调用层解析为 `column_keys` 列表后传入。

## 6. 前端架构

### 6.1 与后端的交互约定

- **开发态**：Vite dev server (`:5173`)，`vite.config.ts` 把 `/api` 代理到 `http://127.0.0.1:18520`（与 main.py 端口起点一致）。
- **打包态**：`npm run build` 产物输出到 `frontend/dist/`，PyInstaller 打入 EXE 的 `_MEIPASS/frontend/dist`。`backend/api/desktop/app.py` 以 `StaticFiles(directory=FRONTEND_DIR, html=True)` 挂载根路径，`html=True` 支持 SPA 回退。pywebview 窗口加载 `http://127.0.0.1:{port}`，前后端同源，`/api` 直达 FastAPI，其余路径返回 index.html。

### 6.2 API 分域

`frontend/src/api/client.ts` 是统一 HTTP Client，`auth.ts`、`users.ts`、`models.ts`、`flights.ts`、`imports.ts`、`analysis.ts`、`sync.ts` 按业务域导出 DTO 与请求函数，`index.ts` 只做分域入口汇总。

- `client.ts` 使用 `BASE = '/api'`，所有请求拼接 `${BASE}${url}`。
- `request<T>()` 自动注入两类 token：
  - `Authorization: Bearer <sessionToken>`：本地会话 token（localStorage `flight_analyzer_session_token`）
  - `x-server-token: <serverToken>`：中心服务器 token（localStorage `flight_analyzer_server_token`），用于本地后端代理调用服务器 API 时透传
- 共享类型由最自然的业务模块持有，调用方使用 `import type`，不再存在单体 `frontend/src/api.ts`。

### 6.3 同步进度轮询

`syncStatus.ts` 本身**不含轮询**，仅提供同步状态工具函数（标签/配色/`deleteScopeFor` 删除范围推断/过滤谓词）。

轮询逻辑在 `features/sync/useSyncOperation.ts`：执行同步操作时生成 `operationId`（`crypto.randomUUID()`），hook 启动定时轮询并调用 `getSyncProgress(operationId)` 更新进度；操作结束或卸载时清理定时器。`SyncPage.tsx` 只组合队列、预览、进度和冲突 UI。

## 7. 桌面壳与启动（`main.py`）

### 7.1 启动流程（`main()`）

## 11. 关键设计约定

开发时请遵守以下约定（源自 `CLAUDE.md` 与代码实现）：

1. **快速迭代，数据无生产价值**：库中现有数据均为测试数据。如确有必要，可直接修改（重建）数据库表结构，无需为兼容旧测试数据做迁移或保留历史字段。但 schema 版本号常量需同步更新。
2. **所有 .txt 类型平等**：导入/格式识别无硬编码白名单，未知类型与已知类型同等处理。
3. **动态表名必须通过 `data_table_name()` 生成**，禁止硬编码。
4. **stored config 单一真相源**：导入复用建机型时存的 config，不复扫。
5. **事务边界**：`import_session` 是唯一的跨模块大事务；其它写操作要么自管小事务，要么把 commit 推给路由层。复杂同步流程的 commit/rollback 时机是稳定契约，不要随意改动。
6. **同步包是跨环境契约**：manifest 字段、ZIP 内路径、SQLite 中间包结构、哈希计算结果必须两端一致。修改需同步两端。
7. **最小依赖打包**：桌面 `requirements.txt` 不含 MySQL/测试依赖；服务器依赖独立在 `requirements-server.txt`。
8. **最小依赖原则**：用 `.venv` 打包，避免 Anaconda 全量环境。
